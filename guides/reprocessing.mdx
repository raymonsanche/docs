---
title: "Event reprocessing"
description: "Retry failed or rejected notification deliveries using different reprocessing strategies"
---

When a webhook notification fails to deliver, the event is marked as rejected. You can reprocess these events to retry delivery instead of losing them. The API provides several reprocessing strategies depending on what you know about the failure.

## When to reprocess events

Reprocess events when:

- A webhook endpoint was temporarily down and notifications were rejected
- A webhook URL was misconfigured and has since been corrected
- A service outage caused delivery failures across multiple clients
- You need to redirect rejected events to a different webhook

## Check rejected events first

Before reprocessing, review which events failed and why. Use the [list rejected events](/api-reference/reprocess/list-rejected-events) endpoint to see failures grouped by event type and webhook:

```bash
curl "/reprocess/rejected-events?legacy_id=12345"
```

The response shows each event type with its webhook-level failure counts:

```json
[
  {
    "event_name": "payment.created",
    "notifications": [
      {
        "webhook_id": "d4e5f6a7-b8c9-0123-4567-890abcdef012",
        "url": "https://example.com/webhook",
        "status": "rejected",
        "count": 15
      }
    ]
  }
]
```

This helps you decide which reprocessing strategy to use.

## Reprocessing strategies

### By trace IDs

Use this when you know exactly which events to retry. This is the most targeted approach.

```bash
curl -X POST /reprocess/by-id \
  -H "Content-Type: application/json" \
  -d '{
    "trace_id_list": [
      "abc123-trace-id-001",
      "def456-trace-id-002"
    ]
  }'
```

Best for: debugging specific failures or retrying a small set of known events.

### By time interval

Use this to retry all events of specific types within a time window. You can scope to one or more clients.

```bash
curl -X POST /reprocess/by-interval \
  -H "Content-Type: application/json" \
  -d '{
    "legacy_id_list": [12345, 67890],
    "event_name_list": ["payment.created"],
    "start_date": "2026-01-15T00:00:00Z",
    "end_date": "2026-01-16T00:00:00Z"
  }'
```

Best for: recovering from service outages that affected a known time period.

<Warning>
Large time intervals with many clients can generate significant load. Use narrow time ranges and specific event names when possible.
</Warning>

### By notification status

Use this to retry all events for a specific webhook and delivery status.

```bash
curl -X POST /reprocess/by-notification-status \
  -H "Content-Type: application/json" \
  -d '{
    "legacy_id": 12345,
    "webhook_id": "d4e5f6a7-b8c9-0123-4567-890abcdef012",
    "status": "rejected"
  }'
```

Best for: retrying all failures for a specific webhook after fixing the endpoint.

### By notification status with redirect

Use this when the original webhook is no longer valid and you want to redeliver events to a different endpoint.

```bash
curl -X POST /reprocess/by-notification-status/redirect \
  -H "Content-Type: application/json" \
  -d '{
    "legacy_id": 12345,
    "webhook_id_old": "d4e5f6a7-b8c9-0123-4567-890abcdef012",
    "webhook_id_new": "f1e2d3c4-b5a6-7890-1234-567890abcdef",
    "status": "rejected"
  }'
```

Best for: migrating from a decommissioned webhook or recovering from a misconfigured endpoint.

<Warning>
The redirect updates the webhook association for all matching rejected events. This operation cannot be reversed.
</Warning>

## How reprocessing works

All reprocessing operations are asynchronous. When you submit a reprocess request, events are queued for redelivery in the background. The API returns immediately with a confirmation message.

To monitor progress, call the [list rejected events](/api-reference/reprocess/list-rejected-events) endpoint periodically. As events are successfully redelivered, they are removed from the rejected list.

## Reprocessing as an issuer

If you are an issuer using the [issuer API](/api-reference/issuer/overview), you can reprocess your own rejected events without specifying a client identifier — it is inferred from your authentication token. See [reprocess by time interval](/api-reference/issuer/reprocess/by-interval) and [reprocess by notification status](/api-reference/issuer/reprocess/by-notification-status) in the issuer API reference.
