---
title: "Reprocess by notification status"
api: "POST /reprocess/by-notification-status"
description: "Reprocess rejected events filtered by webhook and status"
---

Trigger reprocessing of rejected notification events for a specific webhook and delivery status. This re-queues the matching events for delivery in the background.

## Endpoint

```
POST /reprocess/by-notification-status
```

## Request body

<ParamField body="legacy_id" type="integer" required>
  The legacy identifier of the client
</ParamField>

<ParamField body="webhook_id" type="string" required>
  UUID of the webhook whose rejected events you want to reprocess
</ParamField>

<ParamField body="status" type="string" required>
  The notification status to filter by (e.g., `rejected`, `failed`)
</ParamField>

## Request example

```bash
curl -X POST /reprocess/by-notification-status \
  -H "Content-Type: application/json" \
  -d '{
    "legacy_id": 12345,
    "webhook_id": "d4e5f6a7-b8c9-0123-4567-890abcdef012",
    "status": "rejected"
  }'
```

## Response

### Success response (200)

```json
{
  "message": "retry created successfully"
}
```

### No matching events (200)

If no events match the criteria:

```json
{
  "message": "No events were found to resend."
}
```

### Error response (400)

If required fields are missing or invalid:

```json
{
  "error": "bad request"
}
```

## Rules

- All three fields (`legacy_id`, `webhook_id`, `status`) are required
- The `webhook_id` must be a valid UUID
- The `status` must be a non-empty string

## Use cases

- Retry delivery of rejected webhook notifications
- Recover from temporary webhook endpoint failures
- Reprocess events after fixing a webhook URL or configuration

<Note>
Reprocessing is asynchronous. Events are queued and delivered in the background. Use the [list rejected events](/api-reference/reprocess/list-rejected-events) endpoint to monitor progress.
</Note>
